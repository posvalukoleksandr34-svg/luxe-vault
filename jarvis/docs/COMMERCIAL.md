# JARVIS как продукт: аккаунты, тарифы, оплата, админка

По умолчанию JARVIS — **персональная установка**: один владелец, регистрация закрыта, никаких лимитов.
Всё, что описано ниже, включается настройками и нужно только тем, кто хочет дать доступ другим людям
или продавать подписку.

Принцип: **одна система на каждую задачу**. Тарифы — один файл `config/plans.yaml`; права на функции и
лимиты — один сервис `jarvis/billing/service.py`; оплата — один провайдер (Stripe) через вебхуки.

## 1. Аккаунты

| `JARVIS_SIGNUP_MODE` | Кто создаёт аккаунты |
|---|---|
| `closed` (по умолчанию) | только владелец: Админка → Пользователи → «Создать» (или `jarvis create-user`) |
| `invite` | по одноразовой ссылке-приглашению из Админки |
| `open` | любой на странице `/signup` |

* **Подтверждение e-mail и сброс пароля** работают, только если настроен SMTP (`SMTP_HOST`, `SMTP_FROM`, …).
  Без SMTP самостоятельно зарегистрированные аккаунты остаются «не подтверждёнными» (видно в Админке),
  вход им не блокируется, а «Забыли пароль?» честно отвечает, что почта не настроена.
* При настроенном SMTP войти можно только после подтверждения адреса.
* Владелец и аккаунты, созданные владельцем, считаются подтверждёнными.
* Заблокированный в Админке аккаунт теряет все сессии и токены устройств сразу.
* «Настройки → Аккаунт»: скачать все свои данные (JSON), удалить аккаунт (нужны пароль, e-mail и повторный вход).

## 2. Тарифы и лимиты — `config/plans.yaml`

Тариф аккаунта определяется **только на сервере**:
* владелец → `owner_plan` (без ограничений);
* активная подписка (из вебхука Stripe или назначенная владельцем) → её тариф;
* иначе → `default_plan`.

Браузеру тариф не доверяется никогда: он только показывает то, что вернул сервер.

Лимиты (любой можно не указывать = без лимита):

| Лимит | Где проверяется |
|---|---|
| `messages_month`, `messages_per_minute` | каждое сообщение из web, голоса, Telegram, WhatsApp, API v1 (до любой работы) |
| `llm_usd_month` | перед каждым ходом агента, включая автоматизации и фоновые задачи; считается по фактической стоимости токенов из `llm_calls` |
| `custom_commands` | при создании команды (UI, API, инструмент `command_create`) |
| `automations` | при создании автоматизации/напоминания |
| `devices` | при подключении desktop-агента (код 4402, агент ждёт 5 минут) |

Функции (`features`): `computer`, `spotify`, `google`, `browser`, `sandbox`, `voice_premium`,
`custom_commands`, `automations`, `api`. Недоступные по тарифу инструменты просто не предлагаются модели,
а прямые вызовы получают HTTP 402 с понятным сообщением. Без `voice_premium` голос работает через браузер.

Цены в файле — **примеры**. Перед продажей задайте свои и создайте такие же цены в Stripe.

## 3. Оплата — Stripe

1. В Stripe создайте продукты и **recurring**-цены; их id впишите в `.env` (`STRIPE_PRICE_PRO`, …; имя переменной —
   `stripe_price_env` тарифа).
2. `STRIPE_SECRET_KEY` и `STRIPE_WEBHOOK_SECRET` — в `.env` или «Настройки → Ключи».
3. Webhook endpoint: `<JARVIS_PUBLIC_URL>/api/billing/webhook/stripe`, события:
   `checkout.session.completed`, `customer.subscription.created`, `customer.subscription.updated`,
   `customer.subscription.deleted`, `invoice.paid`, `invoice.payment_failed`.
4. Включите Customer Portal в Stripe (отмена, смена карты, смена тарифа).

Как это работает:
* «Перейти на Pro» → Stripe Checkout → после оплаты Stripe шлёт вебхук → сервер проверяет подпись
  (HMAC-SHA256, допуск 5 минут), записывает событие один раз (идемпотентность по id) и меняет тариф.
* Возврат на страницу успеха **не** меняет тариф — только вебхук.
* `past_due` (карта не прошла) — льготный период: тариф сохраняется, пока Stripe повторяет списание;
  `canceled`/`unpaid` — возврат на `default_plan`.
* Данные карт JARVIS не видит и не хранит.

Статус: код написан и покрыт тестами подписи и обработки событий; **с реальным аккаунтом Stripe не
проверялся** (NEEDS AUTH).

## 4. Админка (`/admin`, только владелец)

Пользователи (тариф, блокировка, использование), подписки, сообщения и расходы за месяц, ошибки задач,
обращения в поддержку, приглашения, выключатели функций и режим обслуживания.

* **Выключатели** (`computer`, `spotify`, `custom_commands`, `voice_premium`, `public_api`, `signup`) действуют
  глобально поверх тарифов — «аварийный рубильник» для функции.
* **Режим обслуживания**: всем, кроме владельца, API отвечает 503 с вашим сообщением; вход, публичные страницы,
  админка и вебхуки оплаты продолжают работать.

## 5. Аналитика и мониторинг ошибок

* Аналитика — только счётчики по месяцам в `usage_counters` (`messages`, `event.signup`, `event.checkout_started`…).
  Никакого содержимого, никаких сторонних трекеров.
* Ошибки — структурные логи (`docker compose logs api worker`), метрики Prometheus (профиль `monitoring`),
  упавшие задачи и обращения — в Админке. Внешний сервис ошибок (Sentry и т. п.) **не подключён**.

## 6. Публичный API v1

Токен: «Настройки → Устройства → Скрипт / API» (scope `chat`), тариф с функцией `api`.

```bash
curl -X POST "$URL/api/v1/messages" -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
     -d '{"text":"Какие у меня встречи завтра?"}'
curl "$URL/api/v1/tasks/<task_id>" -H "Authorization: Bearer $TOKEN"      # status, result
curl "$URL/api/v1/usage" -H "Authorization: Bearer $TOKEN"
curl "$URL/api/v1/openapi.json"                                            # схема v1
```

`/api/v1/*` — стабильный контракт; остальные `/api/*` — внутренний API веб-интерфейса и могут меняться.
Версии: `GET /api/version` → `{app, api, schema}`.

## 7. Обновления и откат

`scripts/update.sh` — бэкап → `git pull` → сборка → ожидание готовности; если новая версия не поднялась,
код автоматически откатывается. Откат вручную: `scripts/update.sh --rollback <commit>`. Миграции БД код-откат
не отменяет: если старая версия не стартует на новой схеме — `scripts/restore.sh latest`.

## 8. White-label

`JARVIS_PRODUCT_NAME`, `JARVIS_SUPPORT_EMAIL`, `JARVIS_LEGAL_ENTITY` — имя на входе, в письмах и на страницах
условий. Цвет акцента пользователи выбирают в «Настройки → Внешний вид». Логотип/иконки —
`frontend/public/` (нужна пересборка). Полной мульти-брендовости (разные бренды на одном сервере) нет.

## 9. Масштабирование

API и воркеры — stateless, масштабируются репликами (`docker compose up -d --scale worker=3`); очередь задач —
Postgres `SKIP LOCKED`, события и вызовы устройств — Redis. Кеши тарифов/флагов живут в процессе 10–30 секунд,
поэтому изменение тарифа доходит до других реплик с этой задержкой. Узкое место — один Postgres; для большого
числа пользователей нужен управляемый Postgres с репликами (не входит в поставку).

## 10. Что проверить перед публичным запуском

* Юридические тексты `/legal/terms`, `/legal/privacy` — **шаблоны**, их должен проверить юрист.
* Настроить SMTP (иначе нет подтверждения e-mail и сброса пароля).
* Пройти оплату в тестовом режиме Stripe от начала до конца.
* Бэкапы: проверить восстановление на отдельной машине.
* `JARVIS_PUBLIC_URL` с HTTPS.
